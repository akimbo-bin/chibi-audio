# Outcome-driven delivery operating contract

Policy version: OWNER_OUTCOME_DELIVERY_20261016_V1. Owner direction: 16 October 2026.

## Current authority and precedence
This is the current operating contract for issue ownership, continuity, prioritization, specification depth, review cadence, efficiency and reporting. It supersedes older staffing quotas, minimum-duration/activity requirements, mandatory repeated full-history reads and pause-on-repairable-blocker instructions. Product requirements, historical evidence, current exact-issue acceptance, repository protections, identity/tool permissions, budgets, irreversible-effect controls and personal-machine restrictions remain in force. This policy does not grant new privileges or prove a runtime capability is deployed.

## Durable work, disposable sessions
The work item owns its outcome, acceptance/spec revision, dependencies, branch, exact source head, persistent workspace, attempt history, findings and next action. Continue that work across sessions instead of rediscovering it or forking a duplicate. Reconcile current issue/spec revision, active claims, source head, existing process and uncertain effects before mutation. Hydrate only relevant changed context, not every historical comment on every fire.

Use an authenticated Host lease/checkpoint API only when it is actually available and qualified. Until then, preserve existing GitHub issue claims and Mission handoffs as an explicitly ADVISORY fallback, not an atomic lock. Never take an active/uncertain claim. Expiry does not prove a process stopped; reconcile the owned process before reassignment. Keep bounded source claims (normally about 90 minutes under current policy), exact workspace/head, test evidence and a resumable checkpoint. No transcript or hidden reasoning is required.

## Outcome-directed execution and honest waiting
Finish the next missing acceptance gate. Prefer eligible review, integration, deployment and acceptance over starting unrelated implementation. Repair a genuine blocker using existing authorized operators: reproduce, diagnose, claim a scoped repair, implement, rerun a meaningful test, read back and continue the original objective. Do not replace repair with a ticket or unchanged report. If the required permission, human-use window, budget or dependency is genuinely unavailable, retain ownership and record WAITING with the exact condition and next eligible action. Correct waiting or IDLE_WITH_EVIDENCE is valid; never invent work, findings, commits or elapsed activity to fill a fire.

Repeated eligible attempts without a new finding or relevant tested change require a different hypothesis, an authorized repair or replanning. Repeated polling during a known ineligible interval is not useful work. Record unrelated discoveries as follow-ups without abandoning the assigned outcome unless they truly block it.

## Proportional specifications
Small defect: reproduction, expected behavior, failing oracle, authorized scope and passing regression evidence. Substantial feature: short proposal, behavioral requirements, optional design, bounded tasks and acceptance. New system/major architecture: product intent, boundaries, dependencies, risks, migration/rollback and test strategy before parallel source changes. No mandatory framework installation or design ceremony for a small fix.

## Review, integration and acceptance
Authors self-test appropriate changes. Autonomous scheduled workers require a genuinely different-source-author review of a coherent PR, not independent QA on every commit. Preserve any explicitly owner-scoped review exception, including any explicit task-local review experiment; do not call it independent human/account approval. Owner-directed interactive work retains its authorized self-test/merge distinction. Changed heads invalidate exact-head review. CI, protected branches, source-promotion and actual native/security/release gates remain mandatory.

One integration owner per repository/base at a time; verify the exact merge effect and required post-merge result. A launch, command exit, comment, worker receipt, test fixture, PR or merge is not automatically accepted product behavior. Close the outcome only after its real acceptance oracle passes and evidence is read back. Failed acceptance returns to the same durable work item.

## Roles and concurrency
Director: owns the next accepted milestone, critical dependency, priority and review/integration flow; actively unblocks rather than distributing work for its own sake. Auditor: independently checks outcomes, waste, stale policy, false passes and stalled flow, then makes a bounded evidenced correction. Executor: continues an assigned issue, implements/tests, independently reviews another author's PR, integrates or repairs an authorized dependency. Existing specialized IDs do not require specialized roles. The owner-directed Artist remains an independent creative stream.

Preserve existing routine IDs, enabled states, cadence, models, profiles and project routes. No new scheduler, duplicate browser sender or blind retry of an uncertain external effect. Admission is constrained by genuinely independent READY work, available review/integration capacity, machine eligibility and budget. Admit implementation only to measured review and resource capacity; independently owned creative work and serialized native tests remain separate. Do not increase the fleet to compensate for integration bottlenecks. These are operating limits, not a claim of deployed Host enforcement.

## Evidence and metrics
Distinguish scheduled, delivered, observed working, evidence produced, reviewed and accepted. Record task/routine/fire/attempt IDs and execution origin, observed start/end, actual tools/tests, branch/head, artifacts, result and stop reason. Unknown delivery or attribution stays UNKNOWN, never counted as success, failure or zero effort. Distinguish active time, observed activity span and waiting; never infer useful worker-hours from cadence or fire duration.

Measure accepted outcomes, READY-to-acceptance lead time, review/CI/resource waiting, rework, regressions, cost and owner intervention. DORA's commit-to-production lead time is a separate measure. Do not rank unlike products using crude counts. A policy edit or new validator is not a shipped product milestone.

## Machine and data safety
Keep current machine/OS/profile, native workload custody, secret, rights, spending and destructive-effect restrictions. Personal use wins. Automated heavy native work requires the existing owner-approved time window AND all current human-use/resource/session/owned-process gates; unknown eligibility means NOT_ATTEMPTED, not product failure. Never force logout, close personal apps or remove quarantine markers. Preserve separate manual local-control semantics. Protect private samples/checkpoints and original data; do not publish personal activity, credentials or private transcripts.

## Deployment truth
Repository policy, source tests, installed runtime, live prompt hash and accepted product result are distinct evidence layers. WORKFLOW.md is a versioned contract, not an automatically enabled scheduler/parser. Runtime work-ledger, fencing and event-wake features stay PLANNED until tested, deployed and accepted. Live prompt changes require authenticated revision-fenced operations, immutable receipts and readback. Roll back only the affected field against its current revision; never restore stale scheduler state over intervening fires.
